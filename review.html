Review before implementation

Proposed changes, open flags, and the record of what was decided.

This page exists so that nothing is silently changed. Suggestions sit here with their rationale and their risk until someone with the household's authority accepts or rejects them. Every accepted change is logged with what it altered in the model.

Reading rule

A suggestion is not a recommendation.

It is a candidate improvement to the site or the analysis. It becomes part of the model only after review, and the review is recorded below.

Each one is written so it can be rejected without undoing anything already published. None of them has been implemented.

Proposed changes — status, rationale, risk
#ProposalWhy it would helpRisk if adopted blindlyStatus
S1 Add a “holding-cost stress” path: insurance non-renewal at year 3 forcing a sale in a bad market. Insurability is the least modelled and most likely single cause of a forced sale in a high-fire-score area. It interacts badly with sequence risk. A forced-sale path can be read as a prediction. It must be labelled as a stress test, not a forecast, and it needs a defensible premium trajectory that no public source provides. Overview — the five gates
S2 Model a sibling buy-out as an explicit sub-path with a note and Deed of Trust, rather than as an informal assumption inside the occupancy path. Buying out another beneficiary is the most common way an occupancy decision actually happens, and the financing cost is usually ignored. Requires a household-specific note rate and term. Any published figure would leak financial detail, so the path would have to run on a normalised rate band. Paths model
S3 Split the §121 decision into “qualify by occupancy” and “preserve the exclusion by not renting too early”. The exclusion is lost by a nonqualified-use calculation, not by a single wrong choice. A timing calendar would make it operational. Nonqualified-use rules are fact-specific; a simplified calendar can create false confidence about a 24-of-60-month test. §121 screen
S4 Replace the single “concentration” warning with a measured exposure band for the combined estate, including Property B equity. Property B is usually most of the estate. Treating Property A alone as the concentrated asset understates the exposure. The band would require household equity figures to be meaningful, which conflicts with the no-personal-data rule. A multiples-only version would be less useful but publishable. A ≠ B distinction
S5 Add a “do nothing for 12 months” path with an explicit decision deadline and a written default. Inaction is the most likely real outcome in the first year, and it is currently not a modelled path. Defaults decide more cases than analysis does. A default path can be mistaken for an endorsement of delay; it must state the cost of delay explicitly (carry, insurance gap, vacancy, deferred maintenance). Timeline
S6 Publish a dated “assumption change log” on the assumptions page so that a later reader can see what the model believed on any date. Without it, a six-year-old projection looks current. With it, drift is visible. Adds maintenance burden, and a stale log looks worse than no log. It needs an owner and a review trigger. Assumptions
How to accept a proposal.

Record the decision in the decision log below with the date, the reviewer, the specific change, and what it did to the modelled output. If it changes any published number, regenerate the ranges and robustness counts rather than editing the text.

Interpretation

F1 alone means the occupancy path cannot be assumed.

The allowance is re-indexed every other year, and it covers transfers only through a published window. Any projection that carries today's allowance into the 2040s is a projection of a formula, not of a number — and the formula may itself change.

Two figures not used

Proposed and preliminary items stay out.

The 10% rent-increase limitation is proposed and the parcel-tax result is preliminarily reported. Neither appears in a Property B calculation, and neither should be quoted to a lender or an appraiser as a fact.

Status register

Privacy standard

Nothing identifying is published, including in the build itself

The site is public and the repository history is public. Both are treated the same way.

Enforced by build check
Rule 1 — placeholders only

“Property A” and “Property B”, never an address.

No street, postal area, parcel number, assessor number, owner name, sibling name, employer, or date of a family event appears anywhere in the published pages, the repository, or this build's notes.

Rule 2 — no traceable amounts

Rates, formulas and multiples; no household dollars.

The model runs on a normalised starting value of 1.00 and reports multiples. Where a dollar figure is shown — fees, exemptions, thresholds — it is a published statutory amount, not a household amount, and dollar output is rounded to the nearest $10 so it cannot be matched against a source document.

Rule 3 — combination risk

Removing a name is not anonymisation.

An exact valuation plus a unit count plus an assessed-value trail plus a solar or roof detail can re-identify a property even with every name stripped. The defence is to publish the structure of the decision and withhold the inputs.

Known residual issue

Identifiers exist in historical commit blobs.

Earlier versions of this repository contained a postal area, a city name, a district name, an exact valuation and an assessment figure in committed files. The current tree is clean and the scanner passes, but the earlier objects remain reachable in the public history.

The remediation options are a history rewrite or a fresh public repository seeded from the current tree. The rewrite was documented and deliberately not executed, because it invalidates every clone and fork without the household's instruction to do so.

What is checked automatically

Build fails on a postal-like number or a private name.

  • Five-digit postal-like numbers anywhere in the markup.
  • A blocklist of private place and person terms.
  • Every source-table row must carry a link.
  • Every internal link and anchor must resolve.
  • No tracking scripts, no third-party fonts, no analytics.
